   struct ldd_graph_edge_t:
   - from_tid: Waiting thread ID
   - to_tid: Thread being waited for
   - lock_addr: Lock they're fighting over
   
   Directed graph: A→B means "A waits for lock held by B"

2. EDGE MANAGEMENT
   - Add edge: When thread waits for owned lock
   - Remove edge: When thread acquires lock or gives up
   - Update edge: When ownership changes
   
3. SNAPSHOT ISOLATION
   - Creates immutable copy of graph
   - Detection runs on snapshot (not live graph)
   - Prevents race conditions during analysis

Q: Why use a graph for deadlock detection?

A: "Ma'am, deadlock is fundamentally a graph problem. Circular
   wait condition means cycle in wait-for graph. Graph
   representation makes detection straightforward using DFS.
   Visual: A→B→C→A is a cycle."

───────────────────────────────────────────────────────────────

Q: How do you create an edge?

A: "Ma'am, when state manager reports 'Thread A waiting for
   lock owned by Thread B', I create directed edge A→B.
   Edge stores from_tid=A, to_tid=B, and lock_addr for
   debugging."

───────────────────────────────────────────────────────────────

Q: When do you remove edges?

A: "Ma'am, three cases:
   1. Thread acquires the lock it was waiting for
   2. Thread exits/terminates
   3. Lock is released (no longer blocking anyone)
   
   Edge removal prevents false cycles."

───────────────────────────────────────────────────────────────

Q: What is snapshot isolation?

A: "Ma'am, active graph keeps changing as threads lock/unlock.
   I create immutable snapshot - frozen copy at specific moment.
   DFS runs on this snapshot, seeing consistent state. Without
   this, graph could change during traversal causing errors."

───────────────────────────────────────────────────────────────

Q: Can a thread have multiple outgoing edges?

A: "Ma'am, theoretically yes if thread waits for multiple locks
   simultaneously. But in practice, pthread blocks on first lock,
   so typically 0 or 1 outgoing edge per thread."

═══════════════════════════════════════════════════════════════
🎯 KEY TECHNICAL TERMS:
═══════════════════════════════════════════════════════════════

- Directed edge: One-way relationship (A→B)
- Wait-for graph: Models thread dependencies
- Adjacency list: Efficient edge storage
- Snapshot: Immutable copy for analysis
- Cycle: Circular path (A→B→C→A)

Q: Draw me a deadlock graph

A: "Ma'am, here's a classic 2-thread deadlock:
   
   Thread 100 owns Lock A, wants Lock B
   Thread 200 owns Lock B, wants Lock A
   
   Graph:
   100 ──(wants B)──> 200
    ↑                  │
    │                  │
    └──(wants A)───────┘
   
   This forms cycle: 100→200→100. Deadlock!"

───────────────────────────────────────────────────────────────

Q: What data structure do you use?

A: "Ma'am, adjacency list representation:
   - Array of threads (nodes)
   - Each thread has list of outgoing edges
   - Space: O(V+E) where V=threads, E=edges
   - Lookup: O(1) for adding/removing edges"

───────────────────────────────────────────────────────────────

Q: How do snapshots work internally?

A: "Ma'am, snapshot copies:
   1. All active threads (nodes)
   2. All current edges
   3. Lock addresses for each edge
   
   Deep copy ensures original graph can change without
   affecting snapshot. Snapshot is freed after detection."

───────────────────────────────────────────────────────────────

Q: What if graph becomes huge?

A: "Ma'am, graph size bounded by:
   - Nodes (V) = number of threads (typically 10-50)
   - Edges (E) ≤ V (each thread waits for at most one lock)
   
   Even 100 threads × 100 edges = ~10KB memory. Trivial."

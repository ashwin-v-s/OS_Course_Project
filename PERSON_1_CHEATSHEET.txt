❓ VIVA QUESTIONS YOU'LL GET:
═══════════════════════════════════════════════════════════════

Q: Why binary format instead of text?

A: "Ma'am, binary is much faster - no string formatting overhead
   in the critical path. Text (like JSON/XML) would significantly
   slow down the target program. Binary keeps logging under
   1-2 microseconds per event."

───────────────────────────────────────────────────────────────

Q: Why 28 bytes specifically?

A: "Ma'am, it's the minimum size needed for all required fields:
   1+1+4+4+8+8+2 = 28 bytes. Also aligned for efficient memory
   access on 64-bit systems."

───────────────────────────────────────────────────────────────

Q: What if file is corrupted?

A: "Ma'am, my collector validates schema version first (must be 1).
   Then checks minimum payload length. Rejects malformed events
   gracefully without crashing."

───────────────────────────────────────────────────────────────

Q: What are the 5 event types?

A: "Ma'am:
   1. LOCK_REQUEST (1) - thread attempts lock
   2. LOCK_ACQUIRED (2) - lock granted
   3. LOCK_FAILED (3) - trylock failed
   4. LOCK_RELEASED (4) - unlock called
   5. THREAD_EXIT (5) - thread terminating"

───────────────────────────────────────────────────────────────

Q: How does collector know where event starts?

A: "Ma'am, fixed 28-byte size makes framing simple. Read exactly
   28 bytes, that's one complete event. No delimiters needed."

═══════════════════════════════════════════════════════════════
🎯 KEY TECHNICAL TERMS:
═══════════════════════════════════════════════════════════════

- __attribute__((packed)): Prevents compiler padding
- Schema validation: Ensures version compatibility
- Framing: Reading complete 28-byte chunks
- Binary serialization: Converting data to bytes
- Little-endian: Byte order (LSB first)
